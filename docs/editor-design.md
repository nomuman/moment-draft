# 編集実験の構造

これはローカル検証の設計で、製品の技術構成の決定ではない。プレビューと保存には同じMP4を使う。ブラウザで場面を順次再生する方式も比較したが、映像と音のつなぎ方が書き出しと別実装になるため、この段階では採用しなかった。編集後の再生成待ちは受け入れる。

利用側は、選んだファイルを原本へ照合して初案を作り、場面単位で編集する。

```python
sources = registry.match(descriptors)
plan = baseline(sources)
plan = edit(plan, change, sources)
artifact, path = render(plan, registry, work_dir, ffmpeg)
```

`timeline.py` の不変な `EditPlan` は、順序付きの `Scene` を持つ。画像の長さ、動画の開始・終了、採用状態をここへ集める。内部の時刻は試作の30fps上の整数フレームとし、画面では秒を入力する。合計時間は採用場面から導く。素材を選び直しても編集版番号を増やし、古い画面からの編集を拒否する。

`media.py` の `Registry` だけが原本のパスを持つ。設定したフォルダー内のファイルと、ブラウザで選んだファイルの名前・容量・先頭と末尾のハッシュを照合する。これは全バイトの同一性の証明ではない。一意に照合できない場合は拒否し、読み取り前と書き出し前後に原本の境界・変更を検査する。

`server.py` はループバック接続、許可した経路、要求の検証を担当する。編集とレンダリングは原本パスではなくIDを使う。レンダリングは編集計画のスナップショットを扱い、成功と出力検査が済んでからMP4を公開する。編集後は古い保存リンクを無効にする。

元の音、写真区間の無音、回転、余白、時間の処理は一つのFFmpeg経路にまとめる。実行ファイルは別途指定し、同梱しない。[FFmpegの公式フィルター資料](https://ffmpeg.org/ffmpeg-filters.html)を参照する。

実装は小さなPythonモジュールとブラウザ標準機能に留めた。素材と場面は種類を持つデータクラスで表し、原本の登録と編集操作から生成する。永続的なプロジェクト管理やジョブ基盤は作らない。BGM、Jev、公開サーバーへのアップロード、保存期限の実装は別の未完了事項である。
